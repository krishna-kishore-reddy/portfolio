01 / THE BASICS

What a proxy is, and which direction it faces

A proxy is a server that sits between two parties and passes requests and responses along on behalf of one of them. The word only becomes useful once you say whose behalf.

Forward proxyReverse proxy
Acts on behalf ofThe clients (users, laptops, build servers)The servers (your applications)
Who knows it existsThe client is configured to use it. The server usually sees only the proxy.The client does not know. It believes the proxy is the real server.
Typical jobsCorporate web filtering, outbound access control, anonymity, caching downloadsTLS termination, routing, caching, compression, hiding the backend, rate limiting
Who owns itThe client’s networkThe service owner
Forward proxy:   Client  ->  [Proxy]  ->  Internet / any server
Reverse proxy:   Internet / any client  ->  [Proxy]  ->  Your backend server(s)

NGINX is a reverse proxy by design. The client connects to NGINX, NGINX opens its own separate connection to your application, and the two connections are independent. That separation is the source of nearly every benefit and every gotcha in this article.

02 / THE KEY DISTINCTION

Reverse proxy vs load balancer

Must read — one sentence each: A reverse proxy stands in front of your backend and handles how requests are received and forwarded: TLS, routing, caching, headers, protection. A load balancer decides which one of several equivalent backends should receive each request. A load balancer is therefore a reverse proxy that has more than one place to send traffic and an algorithm for choosing.

People treat these as two products because historically they were: dedicated hardware load balancers did only distribution, and web accelerators did only proxying. NGINX does both with the same engine, so the line is about the job, not the software.

QuestionReverse proxyLoad balancer
Core question it answers“How should this request reach the backend, and what should happen to it on the way?”“Which of these N servers should get this request?”
Backends it needsOne is enoughTwo or more that can do the same work
Main goalsSecurity, TLS offload, routing, caching, one public entry pointScalability, availability, even utilisation, zero-downtime deploys
Decision logicMatch on host, path, headers, then apply rulesAlgorithm (round robin, least connections, hash) plus health and failover
NGINX directiveproxy_pass http://host:port;upstream block with several server lines, then proxy_pass http://group;
If a backend diesThe site is down (single point of failure)Traffic shifts to the remaining servers
Works atLayer 7 (HTTP) in practiceLayer 7 (HTTP) or layer 4 (TCP/UDP)

Three real situations

  • One app on one VM, HTTPS wanted. You need a reverse proxy only. NGINX terminates TLS and forwards to 127.0.0.1:3000. Nothing to balance.
  • Many services behind one domain. Still a reverse proxy: /api/ goes to one service, / to another. Different backends do different jobs, so this is routing, not balancing.
  • Three identical API servers. Now you need a load balancer: the same /api/ request could go to any of three. This is covered in the companion article, NGINX as a load balancer.

Most production NGINX instances are both at once: a reverse proxy in front of the whole estate, which load balances inside each group of replicas.

03 / HOW NGINX THINKS

Config structure and how a request is routed

events { }                      # connection handling
http {                          # everything HTTP lives here
    upstream backend { ... }    # optional named group of servers
    server {                    # one virtual host
        listen 80;
        server_name app.example.com;
        location / {            # one URL rule
            proxy_pass http://backend;
        }
    }
}

Directives are inherited downward unless a lower block sets its own value. This matters for proxy_set_header: if a location defines any proxy_set_header, it stops inheriting all of the parent’s. Repeat every header you want in that location.

Step 1: pick the server block

NGINX matches the connection’s IP and port against each listen. If several server blocks share it, the Host header is compared with server_name (exact, then leading wildcard, then trailing wildcard, then regex). If nothing matches, the default_server for that port handles it, or the first one defined. Set an explicit catch-all that returns 444 so unknown hostnames do not reach your app.

Step 2: pick the location

  1. Exact match location = /path wins immediately.
  2. NGINX finds the longest matching prefix. If that prefix is marked ^~, it wins and regexes are skipped.
  3. Otherwise regex locations (~ case-sensitive, ~* insensitive) are tried in file order. The first match wins.
  4. If no regex matches, the longest prefix from step 2 is used.

Step 3: forward and return

NGINX opens (or reuses) a connection to the upstream, sends the rewritten request, reads the response, and relays it to the client. If the upstream fails, NGINX generates its own error page instead (502, 503, 504).

04 / THE CORE DIRECTIVE

proxy_pass and the trailing slash trap

The most common reverse proxy bug is a single /. The rule: if proxy_pass contains no URI after the host and port, the original request path is sent unchanged. If it contains any URI, even just /, the part of the path that matched the location is replaced by it.

locationproxy_passClient requestsBackend receives
/api/http://b;/api/users/api/users (unchanged)
/api/http://b/;/api/users/users (prefix stripped)
/api/http://b/v2/;/api/users/v2/users (prefix swapped)
/apihttp://b/;/api/users//users (double slash, usually a bug)

Rule of thumb: end both the location and the proxy_pass URI with / when you want to strip a prefix, and use no URI when you want a path passed through. Also note that with a regex location or variables in proxy_pass, you cannot use a URI that way: NGINX passes the request URI as is, so rewrite explicitly if you need to change it.

05 / REAL EXAMPLES

Where is your app? Three common setups

The reverse proxy is the same in every case. What changes is the address NGINX forwards to, and what you must do around it so the setup is safe. Pick the one that matches yours.

A. The app runs on the same server (localhost)

Internet --> NGINX (public :80/:443) --> App (127.0.0.1:3000, same machine)
upstream backend { server 127.0.0.1:3000; keepalive 32; }
server {
    listen 80;
    server_name app.example.com;
    location / { proxy_pass http://backend; }
}

127.0.0.1 is the loopback address: traffic never leaves the machine, so it is fast and cannot be intercepted on a network. The important step is to make the application listen on 127.0.0.1 only (for example app.listen(3000, '127.0.0.1') in Node, or gunicorn --bind 127.0.0.1:8000). Verify with ss -tlnp | grep 3000: you want 127.0.0.1:3000, not 0.0.0.0:3000. If the app listens on every interface and the port is reachable, people can bypass NGINX and skip your TLS and rate limits. Before you configure NGINX, prove the app works with curl -I http://127.0.0.1:3000.

B. The app runs on a different server

Internet --> NGINX server (10.0.1.10) --private network--> App server (10.0.1.20:3000)
upstream backend { server 10.0.1.20:3000; keepalive 32; }

Use the app server’s private IP (or a DNS name). On the app server, allow the port only from the NGINX server, for example sudo ufw allow from 10.0.1.10 to any port 3000, or with a cloud security group. Test from the NGINX machine first: curl -I http://10.0.1.20:3000. If that fails, NGINX will return 502 for the same reason. If the link crosses an untrusted network, use https:// to the backend and add proxy_ssl_verify on;. Hostnames in server are resolved when NGINX starts or reloads, so reload after an IP change. This also means one extra network hop, so keep proxy_connect_timeout short.

C. Several different servers, routed by path

/          --> web server  10.0.1.20:3000
/api/      --> API server  10.0.1.30:8080
/admin/    --> admin app   10.0.1.40:9000
upstream web   { server 10.0.1.20:3000; }
upstream api   { server 10.0.1.30:8080; }
upstream admin { server 10.0.1.40:9000; }
server {
    listen 80;
    server_name app.example.com;
    location /      { proxy_pass http://web; }
    location /api/  { proxy_pass http://api/; }     # trailing / strips /api
    location /admin/{ proxy_pass http://admin/; }
}

This is still a reverse proxy, not a load balancer: each path goes to a different service, so there is nothing to choose between. Users see one domain, which avoids CORS and cookie problems between separate hostnames. Decide for each service whether it expects the prefix: if the API serves /users, strip /api with the trailing slash, as in the table in the previous section. NGINX picks the longest matching prefix, so /api/users goes to the API and not to /.

06 / WHAT THE BACKEND SEES

Headers, client IPs and the Host problem

Because NGINX opens a new connection, the backend sees NGINX’s address as the client. By default NGINX also rewrites Host to the upstream address from proxy_pass (the $proxy_host variable). Applications that build absolute URLs, set cookies per domain or do virtual hosting then misbehave. Pass the original facts along explicitly:

proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
  • $host is the requested hostname without port. Use $http_host if the port must be preserved.
  • $proxy_add_x_forwarded_for appends the connecting IP to any X-Forwarded-For the client already sent, producing client, proxy1, proxy2.
  • X-Forwarded-Proto tells the app the client used HTTPS even though NGINX talks plain HTTP to it. Without it, frameworks generate http:// links and redirect loops.
Spoofing warning: X-Forwarded-For is just a header, and clients can send a fake one. Your app should trust only the last hop(s) it knows. If NGINX itself sits behind a cloud load balancer, use set_real_ip_from <lb-cidr>; and real_ip_header X-Forwarded-For; so $remote_addr becomes the true client before you log or rate limit.
07 / LINE BY LINE

The production location block, explained line by line

This is the block the generator produces. Every line is there for a reason, and each one has a default that is usually wrong for production.

location / {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_connect_timeout 5s;
    proxy_send_timeout 60s;
    proxy_read_timeout 60s;
    limit_req zone=perip burst=20 nodelay;
}
LineWhat it doesIf you leave it out
location / {Applies this block to every URL that no more specific location matches. / is the shortest prefix, so it is the catch-all.Requests have no rule and return 404.
proxy_pass http://backend;Forwards the request to the upstream group named backend (or straight to host:port). No path after the name means the URL is passed unchanged.Nothing is proxied. NGINX tries to serve files itself.
proxy_set_header Host $host;Sends the hostname the user typed (app.example.com) to the backend.The backend receives the upstream name (backend or an IP). Apps that build links or choose a site by hostname break.
X-Real-IP $remote_addr;Passes the real client IP, as NGINX saw it on the connection.The app sees only NGINX’s address in its logs and security checks.
X-Forwarded-For $proxy_add_x_forwarded_for;Passes the chain of addresses the request went through: the client first, then each proxy appended.Apps that read the standard header lose the client IP.
X-Forwarded-Proto $scheme;Tells the app whether the user came in over http or https.The app thinks every request is plain HTTP, creating http:// links, insecure cookies and redirect loops.

proxy_set_header Connection "";Clears the Connection header. NGINX otherwise sends Connection: close, which tells the backend to hang up after each response. Works together with keepalive in the upstream.Connections are closed after every request, so keepalive does nothing.

proxy_send_timeout 60s;Maximum gap between two writes while sending the request to the backend. It matters for slow or large uploads.Default 60s. Fine for most apps. Raise for very slow uploads.
proxy_read_timeout 60s;Maximum gap between two reads while waiting for the backend’s response. It is not the total request time: a response that keeps sending data never times out.Default 60s. Too short for slow reports, too long for no reason on fast APIs.

limit_req in detail

The limit has two parts. First the zone, declared once outside any server: limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;.

  • $binary_remote_addr is the key: each client IP is counted separately. The binary form is compact, so a 10 MB zone tracks roughly 160,000 addresses.
  • zone=perip:10m names the zone and sets its memory size.
  • rate=10r/s is the sustained average. NGINX works in milliseconds, so this means one request every 100 ms.

Then limit_req zone=perip burst=20 nodelay; in the location decides what happens to spikes. Consider a client that sends 30 requests in the same instant, with rate 10r/s and burst 20:

  • No burst: the first request is accepted and the other 29 are rejected, because they arrive faster than one per 100 ms. Real users loading a page would be blocked.
  • burst=20 without nodelay: the first is served and 20 are queued and released one every 100 ms, so the last waits two seconds. The remaining 9 are rejected. Users are not blocked, but they are slowed.
  • burst=20 with nodelay: the first and 20 more are served immediately, and the remaining 9 are rejected. The burst bucket then refills at 10 per second. This is usually best for websites.

Rejected requests get 503 by default. limit_req_status 429; returns the correct “Too Many Requests” code instead. Clients behind one office or mobile NAT share an IP and therefore share a limit. If NGINX sits behind a CDN or load balancer, configure real_ip first, otherwise every request appears to come from the CDN and the limit hits everybody at once.

Two inheritance traps

  • proxy_set_header: if a location defines any proxy_set_header, it ignores every one from the server level. List all headers in the location.
  • add_header: works the same way. A single add_header in a location drops every add_header from the server block. The generator therefore puts security headers inside each location, next to the others.

How to choose the numbers

  • Timeouts: measure your slowest legitimate endpoint in the logs ($upstream_response_time), then set the read timeout 2 to 3 times higher. Keep the connect timeout small.
  • Rate and burst: look at your busiest real user in the access log. Set the rate above their sustained requests per second, and the burst to about twice the rate to cover page loads.
  • Upload size: the largest legitimate file, plus a margin.
  • Keepalive count: start at 32 and raise it if the backend shows many new connections.
08 / TLS TERMINATION

HTTPS at the edge, plain HTTP behind it

TLS termination means NGINX handles encryption with the client, so the certificate lives in one place and backends skip the cryptographic work. Inside a trusted network, NGINX then speaks plain HTTP to the backend. If the hop crosses an untrusted network, use proxy_pass https://... and consider proxy_ssl_verify on; with a CA file so NGINX checks the backend’s certificate.

server { listen 80; server_name app.example.com; return 301 https://$host$request_uri; }
server {
    listen 443 ssl;
    http2 on;                          # nginx 1.25.1+. Older: listen 443 ssl http2;
    server_name app.example.com;
    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
}

On a VM, certbot --nginx obtains a Let’s Encrypt certificate and edits this for you. Automate renewal, and remember NGINX only loads new certificates on reload.

09 / BEHAVIOUR YOU MUST UNDERSTAND

Buffering, timeouts, keepalive, WebSockets and caching

Buffering

With proxy_buffering on (default) NGINX reads the backend’s response as fast as it can into memory (spilling to a temp file if large) and then feeds the slow client from its own buffer. The backend is freed immediately, which is a major reason to put NGINX in front of slow application servers. Turn it off for streaming responses such as server-sent events (proxy_buffering off; or the response header X-Accel-Buffering: no).

Timeouts

  • proxy_connect_timeout (default 60s): time to establish the connection. Lower it, for example to 5s, so failures surface quickly.
  • proxy_send_timeout and proxy_read_timeout (default 60s): maximum gap between two successive writes or reads, not total request time. A slow report endpoint needs a larger read timeout.
  • A 504 Gateway Timeout means a timeout fired. A 502 Bad Gateway means the connection was refused, reset or the response was invalid.
  • client_max_body_size defaults to 1m. Larger uploads get a 413 from NGINX before reaching your app.

Keepalive to the backend

By default NGINX uses HTTP/1.0 to backends and opens a new connection per request. For busy services, reuse connections with an upstream block and proxy_http_version 1.1; proxy_set_header Connection ""; plus keepalive 32; inside the upstream. This removes handshake overhead and exhaustion of ephemeral ports.

WebSockets

WebSocket upgrades use hop-by-hop headers that NGINX does not forward by default. Add proxy_http_version 1.1;, proxy_set_header Upgrade $http_upgrade; and proxy_set_header Connection $connection_upgrade; using a map that yields upgrade or close. Also raise proxy_read_timeout, since the default 60s closes idle sockets.

Caching

Define a zone with proxy_cache_path /var/cache/nginx keys_zone=appcache:10m max_size=1g inactive=60m;, then enable it per location with proxy_cache appcache; and proxy_cache_valid 200 10m;. Only GET and HEAD are cached, and responses carrying Set-Cookie or Cache-Control: private/no-cache are skipped by default. proxy_cache_use_stale error timeout http_502 http_503; serves old content during outages. Never cache per-user pages without a cache key that includes the user.

10 / SECURITY

Hardening a reverse proxy

  • Hide internals: server_tokens off; removes the version number. Never expose the backend port publicly; bind it to 127.0.0.1 or a private network.
  • Rate limit: limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s; then limit_req zone=perip burst=20 nodelay;. Rejected requests return 503 by default, and limit_req_status 429; is friendlier.
  • Limit blast radius: set client_max_body_size, client_body_timeout and client_header_timeout to sensible values.
  • Catch-all server: a default server returning 444 stops host-header scans from reaching your app.
  • Add headers: add_header Strict-Transport-Security "max-age=31536000" always; once HTTPS is solid.
  • Run unprivileged, keep NGINX patched, and limit who can edit config.
11 / WHERE IT RUNS

Linux VM, Docker and Kubernetes

Linux VM (Ubuntu or Debian)

sudo apt install nginx
sudo nano /etc/nginx/sites-available/app.conf
sudo ln -s /etc/nginx/sites-available/app.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

reload is graceful: workers finish current requests while new ones start with the new config. RHEL-family systems use /etc/nginx/conf.d/*.conf instead of sites-enabled.

Docker and Compose

Mount your config at /etc/nginx/conf.d/default.conf. Containers share a network where service names are DNS names, so use http://app:3000. Never use localhost as the backend: inside the NGINX container it means the NGINX container itself. NGINX resolves upstream hostnames once at start, so if the app container is not up it fails with “host not found in upstream”. Use depends_on, and use a resolver 127.0.0.11; with a variable in proxy_pass if backends restart independently.

Kubernetes

You have two patterns. Plain NGINX: a Deployment with the config in a ConfigMap, exposed by a Service, proxying to other Services by their DNS name (http://app.default.svc.cluster.local:3000). The generator below produces this. Ingress or Gateway: Kubernetes also has declarative routing resources. Note that the community ingress-nginx controller was retired in March 2026 with no further releases or security fixes, and the Kubernetes project recommends moving to Gateway API or another supported controller. Do not start new projects on it.

Useful debugging log format: log_format main '$remote_addr "$request" $status $upstream_addr $upstream_status $request_time $upstream_response_time';. Comparing $request_time with $upstream_response_time tells you whether slowness is in the backend or the client link.

Production checklist

  • Run nginx -t in CI and before every reload.
  • HTTPS with automated certificate renewal and an HTTP-to-HTTPS redirect.
  • Pass Host, X-Forwarded-For and X-Forwarded-Proto, and configure the app to trust them.
  • Explicit connect, read and body-size limits. Rate limiting on public endpoints.
  • Backend not reachable except through NGINX.
  • Access and error logs shipped to your logging stack, with upstream timings recorded.
  • A second instance behind a floating IP or cloud load balancer, so NGINX is not a single point of failure.
