Kubernetes, from workload to production

A concise field guide to the objects, scheduling controls, storage, networking, security and autoscaling you commonly configure on real clusters. Use the interactive builder to create editable manifests and copy or download them.

1. Kubernetes objects at a glance

Workload

Pod

Smallest deployable unit. Holds one or more tightly coupled containers that share networking and volumes.

Workload

ReplicaSet

Keeps a specified number of matching Pod replicas running. Usually managed by a Deployment.

Workload

Deployment

Manages stateless replicas and rolling updates, rollbacks and rollout history.

Workload

StatefulSet

For stateful applications needing stable Pod identity, ordered rollout and per-replica storage.

Workload

DaemonSet

Runs a Pod on each eligible node; common for log agents, monitoring and network plugins.

Network

Service

Stable virtual IP/DNS for a changing set of Pods. Common types: ClusterIP, NodePort and LoadBalancer.

Network

Ingress

HTTP/HTTPS routing into cluster Services. Requires an Ingress controller; the object alone does not implement routing.

Storage

PV / PVC

PersistentVolume is storage capacity; PersistentVolumeClaim is a workload's request for storage.

Storage

StorageClass

Describes dynamic provisioning policy, provisioner, reclaim behavior and volume binding mode.

Security

Role / RoleBinding

Grant namespaced permissions and bind them to users, groups or service accounts.

Security

ClusterRole / ClusterRoleBinding

Define cluster-scoped permissions and bind them across the cluster.

Scaling

HPA / VPA

HPA changes replica count; VPA recommends or adjusts container resource requests and limits.

How Kubernetes controllers fit together
You declare the desired state in an API object. A controller continuously compares desired and actual state and takes action. For example, a Deployment manages a ReplicaSet, and the ReplicaSet creates Pods. Do not normally hand-manage ReplicaSets created by a Deployment.

Health probes

Startup probe

Allows slow-starting containers time to initialize. Liveness and readiness checks wait until startup succeeds.

Liveness probe

Detects a stuck or unhealthy process. Repeated failure causes container restart.

Readiness probe

Controls whether the Pod receives Service traffic. Failure removes it from ready endpoints without restarting it.

Probe tuning rule
Choose a probe endpoint that checks the right thing. Avoid making liveness depend on a remote database: a database outage could restart every application Pod. Tune initialDelaySeconds, periodSeconds, timeoutSeconds, failureThreshold and successThreshold to the app's startup and recovery behavior.

Scheduling: taints, tolerations and affinity

FeatureDirectionTypical use
NodeSelectorPod requires matching node labels.Pin GPU workloads to nodes labelled accelerator=nvidia.
Node affinityPod requires or prefers node labels.Required or preferred placement by zone, hardware or node pool.
Pod affinityPlace near other matching Pods.Co-locate app and local cache in the same zone/node domain.
Pod anti-affinityAvoid matching Pods in a topology domain.Spread replicas across nodes or zones to reduce correlated failure.
TaintNode repels Pods unless tolerated.Reserve nodes for critical, GPU or infrastructure workloads.
TolerationPod is allowed onto a tainted node.Permit a workload on a dedicated node; it does not force placement there.
# Taint a dedicated node
kubectl taint nodes worker-1 workload=gpu:NoSchedule
# Remove the taint (note the trailing minus)
kubectl taint nodes worker-1 workload=gpu:NoSchedule-
# Inspect labels and taints
kubectl get nodes --show-labels
kubectl describe node worker-1

Container security and reliability

  • Run as non-root where possible; set runAsNonRoot, runAsUser and fsGroup deliberately.
  • Set allowPrivilegeEscalation: false, drop Linux capabilities, and use readOnlyRootFilesystem: true when compatible.
  • Prefer seccomp RuntimeDefault; avoid privileged containers unless a justified node-level agent requires them.
  • Use resource requests for scheduling and limits to constrain consumption. CPU limits can throttle; memory limit breaches can cause OOM kills.
  • Use Secrets for sensitive values, restrict access with RBAC, and consider external secret management and encryption at rest.
  • Use PodDisruptionBudget for voluntary disruptions; it does not protect against every involuntary failure.

Ingress

Ingress routes HTTP(S) host/path traffic to Services. Install and configure an Ingress controller (for example, NGINX or a cloud controller) and a suitable IngressClass. For new advanced gateway use cases, evaluate Gateway API support in your cluster.

NetworkPolicy reminder
NetworkPolicy is a separate API resource used to allow/deny Pod traffic. It only has effect when the installed CNI plugin implements NetworkPolicy. Start with default-deny in sensitive namespaces, then explicitly allow required ingress and egress.

5. RBAC and service account security

Least-privilege RBAC checklist
Avoid wildcard verbs/resources. Grant only the verbs and API groups required. Prefer namespace-scoped RoleBindings when possible. Do not give application service accounts cluster-admin. Disable automatic service-account token mounting when the Pod does not need Kubernetes API access.
# Check effective permissions
kubectl auth can-i get pods -n production --as=system:serviceaccount:production:api-sa
kubectl auth can-i '*' '*' --as=system:serviceaccount:production:api-sa
# Inspect bindings
kubectl get role,rolebinding -n production
kubectl get clusterrole,clusterrolebinding

6. Autoscaling

HPA — Horizontal Pod Autoscaler

Changes the number of replicas based on CPU, memory or custom/external metrics. CPU utilization needs resource requests to calculate utilization correctly.

VPA — Vertical Pod Autoscaler

Recommends or adjusts container CPU/memory requests. Requires VPA components installed separately; it is not built into every Kubernetes cluster.

HPA vs VPA in production
HPA scales out/in; VPA right-sizes per-Pod resources. Avoid having HPA and VPA both control CPU/memory in conflicting ways. A common pattern is HPA on a custom metric plus VPA recommendations, or HPA on CPU with VPA managing memory only, depending on the VPA mode and workload. Test evictions and disruption behavior before enabling automatic updates.
kubectl get hpa -A
kubectl describe hpa api -n production
kubectl top pods -n production
kubectl top nodes

Not every resource has a useful kubectl create generator. StatefulSet, DaemonSet, Ingress, PV/PVC, StorageClass, VPA and advanced HPA configurations are usually authored as YAML. For client-side validation use kubectl apply --dry-run=client -f manifest.yaml; for API-server validation use kubectl apply --dry-run=server -f manifest.yaml.


# Safe review workflow
kubectl diff -f ./manifests/
kubectl apply --dry-run=server -f ./manifests/
kubectl apply -f ./manifests/
kubectl rollout status deployment/api -n production
kubectl get pods,svc,ingress -n production -o wide



9. Production rollout and troubleshooting checklist




Before deploy
Namespace, image tag pinned, resource requests/limits, probes, security context, secrets, RBAC, network policy, storage and replica strategy.


During deploy
Server-side dry run, diff, rollout status, readiness, events, endpoint checks and application-level smoke tests.


After deploy
Metrics, logs, alerts, HPA behavior, backup/restore test, PDB, capacity and rollback procedure.
