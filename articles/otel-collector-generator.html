01 / THE PROBLEM

Why do we need the OpenTelemetry Collector?

Modern applications run across containers, Kubernetes, virtual machines, managed databases and cloud services. Each component can produce telemetry in a different format and often has a different integration method for each monitoring backend.

Without a common collection layer, teams end up maintaining multiple agents, vendor-specific SDK integrations, custom forwarding scripts and duplicated configuration. A backend migration can then require changes across many applications.

OpenTelemetry Collector is a vendor-neutral telemetry pipeline. It receives telemetry, optionally enriches or transforms it, and exports it to one or more observability backends. Applications can send OTLP to the Collector instead of being coupled directly to a particular vendor.
  • Centralize telemetry collection and routing.
  • Separate application instrumentation from backend destinations.
  • Apply batching, filtering, enrichment and sampling consistently.
  • Reduce direct application-to-vendor coupling.
  • Support multiple destinations and migration strategies.
02 / PIPELINE

How the Collector works

A Collector pipeline is built from three main component types. Components must be enabled in the service pipelines to become active.

RECEIVERSAccept telemetry
PROCESSORSEnrich / filter / batch
EXPORTERSSend telemetry
BACKENDSStore / query / alert

Receivers ingest data through protocols or sources such as OTLP, host metrics, files and Prometheus scrape endpoints. Processors modify or control data in flight. Exporters deliver the resulting telemetry to destinations.

Agent and gateway patterns

  • Agent: a Collector runs close to the workload, commonly as a Kubernetes DaemonSet or a VM service. It reads local files, host metrics and application telemetry.
  • Gateway: a horizontally scalable Collector service receives telemetry from agents or applications, centralizes processing, and exports to backends.
  • Hybrid: agents handle node-local collection while gateways handle shared processing, routing and backend credentials.

03 / TELEMETRY

Logs, metrics and distributed traces

Logs

Timestamped records describing events. A filelog receiver can tail application log files; Kubernetes node agents can collect container log files. Parse and enrich records carefully, and avoid collecting secrets or unnecessary personal data.

Metrics

Numeric measurements over time, such as request rate, error count, latency histograms, CPU and memory. Host metrics and Prometheus receivers are common sources. Metrics are useful for dashboards, alerting and capacity analysis.

Traces

A trace follows a request across services. Spans capture individual operations and their parent-child relationships. OTLP is the common transport; trace context propagation in application code is essential for end-to-end traces.

Must read — pipeline basics: A Collector can handle all three signals, but each signal needs its own pipeline and compatible receiver/exporter components. Selecting a receiver does not automatically create a pipeline.
04 / ELASTIC INTEGRATION

Using OpenTelemetry with Elasticsearch and Kibana

Elasticsearch stores and indexes data; Kibana provides search, visualization and operational workflows. The Collector can send supported telemetry to Elasticsearch using the Elasticsearch exporter, or send OTLP to an OpenTelemetry-compatible intake path where appropriate.

A typical architecture is:

Apps / Kubernetes / VMs
          |
          v
   OpenTelemetry Collector
          |
          |  Elasticsearch exporter
          v
    Elasticsearch cluster
          |
          v
        Kibana
   Discover / Dashboards

For a production design, decide how logs, metrics and traces should be indexed, mapped, retained and secured. Verify the exporter and backend versions you deploy, and test the exact signal mapping before rolling it out widely. Kibana data views / data views or integrations may need to be configured before data appears in Discover.

For the Collector-to-Elasticsearch connection, use TLS verification, a least-privilege credential, and a Kubernetes Secret or protected VM environment file. Do not commit API keys or passwords into Git.

05 / CHOOSING AN INGESTION LAYER

OpenTelemetry Collector vs ELK and EFK

Must read — what the names mean: ELK is Elasticsearch, Logstash and Kibana. EFK is Elasticsearch, Fluentd (or Fluent Bit) and Kibana. The “C” in ECK means Cloud on Kubernetes; it is Elastic’s Kubernetes Operator, not the OpenTelemetry Collector. This section compares the Collector with the ELK/EFK ingestion agents.

OpenTelemetry Collector is backend-agnostic. It accepts telemetry through supported receivers, processes it in signal-specific pipelines, and exports it to compatible backends. You can send different signals to different destinations, or configure multiple exporters for a signal when fan-out is needed. The Collector is not limited to Elasticsearch.

Where the Collector can help

  • Decouple apps from vendors: instrument once with OpenTelemetry APIs/SDKs and OTLP, then change or add backends mainly in Collector configuration rather than rewriting application instrumentation.
  • One pipeline for three signals: collect and process logs, metrics and traces with shared operational patterns, while keeping each signal’s pipeline and exporter compatibility explicit.
  • Route and fan out: send supported telemetry to one or more compatible destinations, for example during a backend migration or parallel validation.
  • Standardized processing: batch, enrich, filter, redact and sample telemetry before export, using common Collector components and configuration.
  • Flexible deployment: run agents close to workloads as DaemonSets or VM services, gateways centrally, or combine both patterns.
  • Broader ecosystem: use receivers, processors and exporters from the core or Contrib distributions; confirm each component and option is supported by the exact build and version you deploy.

Important correction: Fluent Bit, Fluentd and Logstash are not inherently restricted to a single backend. They can be configured with multiple outputs/destinations (subject to plugins, pipeline design and supported data formats). Their ecosystems are commonly used for log collection and processing; OpenTelemetry Collector’s distinguishing advantage is its vendor-neutral, multi-signal telemetry model and standardized OTLP ecosystem—not an exclusive ability to send to multiple backends.

These tools can also be combined. For example, an existing Fluent Bit or Logstash deployment can forward data to an OpenTelemetry Collector, or the Collector can send data to an Elasticsearch-based stack. Choose based on required sources, processing features, operational familiarity, resource limits and backend support; the Collector is not automatically a replacement for every ELK/EFK capability.

06 / KUBERNETES

Deploying with the OpenTelemetry Operator

Install the OpenTelemetry Operator and its required cert-manager dependency according to the Operator documentation for your Kubernetes distribution. The Operator introduces the OpenTelemetryCollector custom resource definition (CRD). You declare the Collector configuration and deployment strategy; the Operator reconciles the corresponding Kubernetes resources.

Must read — Kubernetes file logs: Run filelog as a node agent (usually a DaemonSet) and mount the host log directories the receiver reads. For Docker nodes, the generated manifest must mount both /var/log/pods and /var/lib/docker/containers, because pod log paths can resolve through symlinks into Docker’s container log directory.
  • Deployment: suitable for a central gateway or a horizontally scalable stateless Collector service.
  • DaemonSet: one Collector pod per eligible node; useful for node-local logs, host metrics and kubelet-related collection.
  • StatefulSet: useful when stable pod identity or persistent storage is required by the chosen design. It is not automatically the best choice for every Collector.

Choose the strategy based on data locality, scaling, persistence and failure-domain requirements. Avoid collecting the same host or pod logs multiple times when combining agents and gateways.

apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: platform-collector
  namespace: observability
spec:
  mode: deployment
  image: otel/opentelemetry-collector-contrib:0.165.0
  config:
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
          http:
            endpoint: 0.0.0.0:4318
    processors:
      memory_limiter:
        check_interval: 1s
        limit_percentage: 75
        spike_limit_percentage: 15
      batch: {}
    exporters:
      debug:
        verbosity: basic
    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [debug]

This is an illustrative starter manifest, not a universal production configuration. CRD API versions, image tags and component availability depend on the Operator and Collector release you install.

07 / VIRTUAL MACHINES

Deploying on Linux virtual machines

For VMs, install a compatible Collector Contrib distribution and run it as a systemd service. Keep the YAML configuration separate from the binary and service definition. Use a protected environment file for credentials, restrict file permissions, and grant the service account only the host access it needs.

The generator below can produce a Collector config, a sample systemd unit and an installation helper. Review the package URL, architecture, checksum and service permissions for your OS before running an installation script in production.

DEPLOY AND VERIFY

Apply it and check that data arrives

Kubernetes

  • Create the Secret with the command in the Secrets tab. Do not commit real values.
  • If ServiceAccount/RBAC generation is enabled, apply its YAML before the Collector CR: kubectl apply -f service-account-rbac.yaml -f your-collector.yaml. If disabled, the Operator creates its default ServiceAccount; Kubernetes API receivers and metadata enrichment need suitable permissions added separately.
  • Watch the pods and read their logs: kubectl get pods -n observability and kubectl logs -n observability -l app.kubernetes.io/component=opentelemetry-collector --tail=50.
  • While testing, add the debug exporter to one pipeline to see records in the log. Remove it afterwards.

Virtual machines

  • Run bash install.sh. Set SHA256 first if you want the download verified, using the value from the release page.
  • Fill in /etc/otelcol/otelcol.env before the first start. Check with systemctl status and journalctl -u otelcol-contrib -f.

Elasticsearch and Kibana

With the default routing, documents go to data streams named logs-<dataset>-<namespace>, and the same for metrics and traces. In Kibana, open Stack Management, then Index Management, then Data Streams, and confirm they exist and grow. Create a data view such as logs-* to search them in Discover. Retention and rollover belong to Elasticsearch (data stream lifecycle or ILM), so set them there.

The API key needs permission to write to those data streams. Grant create_doc and auto_configure on logs-*-*, metrics-*-* and traces-*-*, and check Elastic's exporter documentation for the exact privileges your version needs.

08 / PRODUCTION READINESS

Production checklist

  • Set memory limits and configure the memory_limiter processor early in each pipeline.
  • Use batch processing and size queues / retries for the expected traffic and backend availability.
  • Secure OTLP endpoints with TLS and authentication where traffic crosses trust boundaries.
  • Use Secrets or protected environment files; never hardcode credentials.
  • Apply Kubernetes resource requests / limits and appropriate RBAC.
  • Monitor Collector health, refused / dropped data, queue saturation and exporter failures.
  • Plan for cardinality, sampling, retention, cost and personally identifiable information.
  • Pin and test Collector versions; verify component availability in the selected distribution.
  • Roll out gradually and validate end-to-end delivery for each signal.
