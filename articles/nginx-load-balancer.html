01 / THE PROBLEM

Why load balance at all?

A single application server has three limits: capacity (it can only handle so many requests), availability (when it dies, the service dies), and deployability (restarting it means downtime). Running several identical copies fixes all three, but only if something spreads traffic across them and notices when one is unhealthy. That something is a load balancer.

Must read — reverse proxy vs load balancer: a reverse proxy forwards client requests to a backend and handles TLS, routing, caching and headers. A load balancer is a reverse proxy with several equivalent backends that also chooses which backend gets each request and stops using ones that fail. In NGINX the first uses proxy_pass to one server; the second adds an upstream block with many servers. The full comparison is in NGINX as a reverse proxy. This article is about the choosing and failover logic.

02 / LAYER 7 VS LAYER 4

HTTP balancing or TCP balancing

Layer 7 (http module)Layer 4 (stream module)
NGINX seesFull HTTP requests: URL, headers, cookiesRaw TCP or UDP connections
Can route onHost, path, headers, cookiesOnly IP and port
Can terminate TLS, cache, rewriteYesTLS termination only, no HTTP features
Typical useWeb apps, APIs, WebSocketsDatabases, MQTT, SMTP, DNS, passing TLS through untouched
Confighttp { upstream ... proxy_pass http://x; }stream { upstream ... proxy_pass x; } (top level, outside http)

Choose layer 7 unless you need protocol-agnostic balancing or end-to-end TLS you must not decrypt. The stream block lives in nginx.conf itself, not in conf.d or sites-enabled, which are included inside http.

03 / ANATOMY

The upstream block and server parameters

upstream backend {
    least_conn;                                   # algorithm (default: round robin)
    zone backend 64k;                             # shared memory: state shared by all workers
    server 10.0.0.11:8080 weight=3;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 backup;
    keepalive 32;                                 # idle connections kept open per worker
}
server {
    location / { proxy_pass http://backend; }
}
ParameterMeaning
weight=NRelative share of traffic. Default 1. A weight-3 server gets about three times the requests of a weight-1 server.
max_fails=NConsecutive failed attempts within fail_timeout before the server is considered unavailable. Default 1. 0 disables the check.
fail_timeout=TBoth the window in which failures are counted and how long the server is then skipped. Default 10s.
backupUsed only when all primary servers are unavailable.
downMarks a server as permanently out of rotation (useful for draining before maintenance).
max_conns=NCap on simultaneous connections to that server. Default 0 (no limit). Excess requests go elsewhere or fail.

Without zone, each NGINX worker process keeps its own failure counters and connection counts, so with four workers a server may need to fail in each of them separately. Adding a zone shares this state across workers, which makes least_conn, max_conns and max_fails behave as you expect.

04 / LINE BY LINE

The load balancer location block, explained line by line

location / {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_connect_timeout 3s;
    proxy_send_timeout 60s;
    proxy_read_timeout 60s;
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 3;
    proxy_next_upstream_timeout 10s;
    limit_req zone=perip burst=40 nodelay;
}
LineWhat it doesLoad balancer detail
proxy_pass http://backend;Sends the request to the upstream group named backend.With a group name, NGINX picks one of its servers using your algorithm. With a single host:port there would be no choice.
proxy_set_header Host $host;Passes the hostname the user typed.Every backend sees the same public hostname, so any of them can build correct links.
X-Real-IP, X-Forwarded-ForPass the real client IP, and the chain of proxies.Without them every backend logs the load balancer’s address, and per-client logic and rate limits fail.
X-Forwarded-Proto $scheme;Tells backends whether the client used HTTPS.The load balancer terminates TLS and speaks plain HTTP to backends, so this header is the only way they know.
proxy_http_version 1.1; and Connection ""Enable persistent connections to backends.Pair with keepalive in the upstream. Without them every request opens a new connection to whichever backend was chosen.
proxy_connect_timeout 3s;Time allowed to connect to one backend.Failover speed: when a server is dead, a client waits this long before NGINX tries the next one. The default of 60s would be a minute.
proxy_send_timeout, proxy_read_timeoutGap allowed between two writes, or two reads, with one backend.A read timeout counts as a failure towards max_fails and can trigger a retry on another server.
proxy_next_upstream error timeout http_502 http_503 http_504;Lists which failures make NGINX retry the request on the next server.Default is only error timeout. Adding the HTTP codes hides most backend failures from users. Do not add http_500 blindly, since a bug that returns 500 would be retried on every server.
proxy_next_upstream_tries 3;Maximum number of servers tried per request, including the first.Prevents a retry storm. Keep it at or below your number of active servers.
proxy_next_upstream_timeout 10s;Total time budget for all attempts of one request.Stops a request bouncing between slow servers forever. Should be longer than the connect timeout times the tries.
limit_req zone=perip burst=40 nodelay;Per-client rate limit with a burst allowance.Protects the whole pool from one client. The rate, burst and nodelay behaviour are explained in the reverse proxy article.

How to choose the numbers

  • max_fails and fail_timeout: 3 failures in 30s is a sound start. Lower values react faster but remove healthy servers after one hiccup, and if every server is paused NGINX returns 502 to everyone.
  • Connect timeout: 3 to 5 seconds on a healthy private network.
  • Tries: 2 or 3, never above the number of active servers.
  • Weights: proportional to capacity. A server with twice the CPUs gets weight=2.
  • Keepalive: 32 per worker is a good start; raise it if backends show many new connections.
05 / CHOOSING A BACKEND

Load balancing algorithms in depth

Round robin (default)

Requests go to servers in turn: 1, 2, 3, 1, 2, 3. With weights, NGINX uses a smooth weighted variant, so weights 5, 1, 1 produce a mixed sequence rather than five requests in a row to the first server. Best when requests cost about the same and servers are similar. It ignores how busy a server is, so a few slow requests can pile up on one node.

least_conn

Sends each request to the server with the fewest active connections (weighted by weight). Best when request durations vary a lot, such as a mix of quick API calls and long downloads or reports. It adapts to slow servers automatically. It needs correct connection accounting, so add a zone.

ip_hash

Hashes the client’s IP (the first three octets for IPv4) so the same client keeps going to the same server while it is available. Gives crude session stickiness. Caveats: many users behind one NAT or proxy all land on one server, and removing a server reshuffles clients. If NGINX is behind another proxy, enable realip first or every client will look identical. You cannot combine ip_hash with backup servers.

hash key [consistent]

Chooses the server from a hash of any variable, for example hash $request_uri consistent; (good for cache locality) or hash $cookie_sessionid consistent; (sticky sessions by cookie value). The consistent flag uses ketama hashing, so adding or removing a server remaps only about 1/N of the keys instead of nearly all of them.

random two least_conn

Picks two servers at random, then the one with fewer connections. This avoids the herd effect where many balancers all pick the same “least loaded” server, and works well with several NGINX instances.

AlgorithmPick it whenAvoid it when
Round robinUniform requests, identical servers, stateless appRequest cost varies widely
least_connMixed fast and slow requests, long-lived connectionsYou forgot zone with multiple workers
ip_hashQuick stickiness without app changesClients share IPs (NAT, proxies)

06 / FAILURE HANDLING

Health checks, retries and what open-source NGINX does not do

Open-source NGINX uses passive health checks: it learns a server is bad only when a real request fails. After max_fails failures inside fail_timeout, the server is skipped for fail_timeout, then one trial request is allowed through. A user request is the probe, so some users hit failures before the server is removed.

What counts as a failure, and the retry behaviour

proxy_next_upstream error timeout; is the default: connection errors and timeouts trigger a retry on the next server. HTTP error responses such as 502 or 503 are not retried unless you list them: proxy_next_upstream error timeout http_502 http_503 http_504;. Bound the damage with proxy_next_upstream_tries 3; and proxy_next_upstream_timeout 10s;.

Retry safety: NGINX does not retry non-idempotent requests (POST, LOCK, PATCH) once they have been sent, unless you add non_idempotent. Retrying a payment POST could charge twice, so leave it off unless the endpoint is idempotent. Also beware retry storms: if every request retries three times against a struggling pool, you triple the load at the worst moment.

Not available in open-source NGINX

  • Active health checks (health_check) that probe backends on a timer.
  • slow_start to ramp traffic to a recovered server.
  • Cookie-based sticky sessions with NGINX-managed cookies (use hash $cookie_... with an application cookie instead).
  • A live API to add and remove servers without reload, and request queuing with queue.

Common open-source answers are making health explicit in the app (return 5xx quickly when unhealthy), using nginx -s reload to apply changes (graceful, no dropped connections), and putting an external controller or service discovery in charge of the server list.

07 / STATE

Sessions and sticky routing

The best design is a stateless app: sessions in Redis or a database, so any server can serve any request. Then plain round robin or least_conn is enough and failover is invisible. If you cannot do that, use ip_hash or hash $cookie_sessionid consistent;. Stickiness is a weaker guarantee than it sounds: when the pinned server fails, the user is moved and their local session is lost, so it is a performance aid, not a reliability feature.

08 / PERFORMANCE

Connection reuse and capacity

Put keepalive 32; in the upstream, and in the location set proxy_http_version 1.1; and proxy_set_header Connection "";. Without them NGINX opens a new TCP connection for each request, wasting time and ephemeral ports. The keepalive number is idle connections per worker, not a total cap. Check worker_processes auto; and worker_connections (each proxied request uses two connections: one to the client, one to the backend), and the process file limit worker_rlimit_nofile. Use max_conns to protect fragile backends.

09 / THE LOAD BALANCER ITSELF

Do not create a new single point of failure

One NGINX in front of three servers moves the risk to NGINX. Run two or more NGINX nodes with identical config. Common ways to share one address: keepalived (VRRP floating IP between two VMs), a cloud load balancer in front of several NGINX instances, or DNS with several records (slow to fail over because of caching). Keep config in Git and validate it with nginx -t in CI so both nodes stay identical.

10 / WHERE IT RUNS

Linux VM, Docker and Kubernetes

Linux VM

List backends by private IP or DNS name in the upstream. Put the file in sites-available and link it, test with nginx -t, and reload. For TCP balancing, add the stream block to /etc/nginx/nginx.conf.

Docker

Upstream names such as app1:8080 are resolved once at startup. If a container restarts and gets a new IP, NGINX keeps the old one until reloaded. For a scaled service (docker compose up --scale app=3), the single name app resolves to several IPs at start, and NGINX will balance across the addresses it saw, but will not notice later scaling without a reload. Start NGINX after backends (depends_on) and reload when the set changes.

Kubernetes

A Kubernetes Service already load balances across pods, but at layer 4 and per connection, so with long-lived HTTP/2 or keepalive connections load can be uneven. Pointing NGINX at the Service name gives you simple L7 features on top. To balance across individual pods yourself, use a headless Service, though open-source NGINX resolves names only at start-up, so pod churn needs reloads or a controller. Because of that, most clusters use an Ingress or Gateway API implementation instead. The community ingress-nginx controller was retired in March 2026 with no further fixes, and the Kubernetes project recommends Gateway API or another supported controller for new work.

11 / OPERATING IT

Observability, testing and checklist

Log which backend answered every request:

log_format lb '$remote_addr "$request" $status '
              'up=$upstream_addr ust=$upstream_status urt=$upstream_response_time rt=$request_time';
access_log /var/log/nginx/lb.log lb;

If a request was retried, $upstream_addr lists several addresses separated by commas, and $upstream_status lists each result. Add stub_status on a private port for connection counts.

Prove it works

  1. Run for i in $(seq 1 12); do curl -s http://lb.example.com/whoami; echo; done and confirm the spread matches your algorithm and weights.
  2. Stop one backend and repeat. Expect a few errors, then traffic only to the survivors.
  3. Start it again and confirm it returns to rotation after fail_timeout.
  4. Check the log: failed attempts should show up as multiple $upstream_addr values.

Production checklist

  • At least two backends and two NGINX nodes, with a floating IP or cloud LB in front.
  • A zone in every upstream, and a deliberate algorithm choice.
  • Sensible max_fails, fail_timeout, connect timeout and bounded retries.
  • No retries for non-idempotent requests unless the endpoint is safe.
  • Keepalive to backends, and enough file descriptors and worker connections.
  • Upstream timings in logs, with alerts on 5xx rate and latency.
  • A drain procedure: mark down, reload, wait for connections to finish, then deploy.
